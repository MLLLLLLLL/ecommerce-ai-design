# 营销助手2开发实施文档 V2

## 1. 文档信息

- **文档状态**：V2 方案，待技术评审后实施
- **目标入口**：`/marketing2`
- **对应设计**：`营销助手2_交互设计文档V2.md`
- **基础文档**：`电商主图 & 详情页 AI 全自动化生成工作流.md`
- **V1 文档**：`营销助手2_开发实施文档.md`
- **实施原则**：先完成高风险契约和模型安全边界，再实现 UI；不影响旧营销助手和通用工作流。

## 2. 当前基线与实施结论

### 2.1 已有能力

- `src/app/(dashboard)/marketing2/page.tsx` 已存在入口，但仍是占位页面。
- `src/app/api/model-configs` 提供服务端多文本模型的安全摘要和配置接口。
- `ModelConfig` 已支持 `vision`、`jsonMode`、`ocr`、`imageGeneration` 标签和实测状态。
- `MarketingTask`、`MarketingTaskItem`、`MarketingTaskEvent` 已具备任务、子任务、重试和事件基础设施。
- 旧营销模块已有产品分析、文案、主图提示词和详情页提示词引擎。

### 2.2 V2 架构决策

1. 营销助手2使用业务工作流运行器，不直接复用无限画布作为首期 UI。
2. 服务端 `ModelConfig` 是营销助手2文字和图片模型的唯一来源。
3. 前端只传 `workflowKey`、业务输入、模型 ID 和版本号，不传 API Key、Base URL 或完整配置。
4. 工作流卡片、输入输出、步骤依赖和模型能力由版本化注册表统一定义。
5. 任务状态和步骤状态由服务端唯一维护，使用版本号和幂等键防止重复执行。
6. 图片生成和返修永远创建新资产版本，不覆盖原图。

## 3. 总体架构

```text
工作流卡片中心
        ↓ workflowKey
工作流运行页
        ↓
Workflow Registry（版本化契约）
        ↓
Marketing2 Run Service
        ↓
MarketingTask + MarketingTaskItem + MarketingTaskEvent
        ↓
Step Executor
        ↓
Model Resolver -> ModelConfig -> Text/Image Adapter
        ↓
文件存储 -> Asset 版本 -> 导出
```

## 5. 模型配置、迁移和能力测试

### 5.1 统一能力模型

扩展现有 `ModelCapabilities`：

```ts
interface ModelCapabilities {
  vision: boolean;
  jsonMode: boolean;
  ocr: boolean;
  imageGeneration: boolean;
  imageEditing: boolean;
  referenceImage: boolean;
}
```

`imageGeneration` 表示可生成图片，`imageEditing` 表示可对已有图片进行编辑或图生图，`referenceImage` 表示供应商能稳定接收参考图。三者不能互相推断。

### 5.2 设置迁移

当前图片服务配置与服务端文本模型配置存在两条链路。V2 要求：

1. 在设置页提供旧图片服务配置迁移预览。
2. 用户确认后，将配置写入服务端 `ModelConfig`，API Key 只在服务端加密保存。
3. 迁移失败不删除旧配置。
4. 迁移完成前，营销助手2只允许使用已经服务端保存的模型。
5. 旧图片页面可以继续兼容旧配置，但营销助手2不得读取浏览器密钥作为运行时配置。

### 5.3 能力实测

扩展模型测试接口，至少包含：

| 测试 | 输入 | 通过标准 |
|---|---|---|
| `connection` | 简短文本 | 2xx 且有文本响应 |
| `jsonMode` | 固定 JSON 请求 | 可解析并通过 Schema |
| `vision` | 内置测试图片 | 返回可验证的图片描述 |
| `imageGeneration` | 短提示词 | 返回可下载图片并通过文件校验 |
| `imageEditing` | 测试图片+编辑指令 | 返回图片且主体未丢失 |
| `referenceImage` | 测试图片+生成指令 | 返回图片且请求确实带参考图 |

设置页、模型 API、Prisma JSON 字段和营销模型选择器必须同步支持新增能力。能力未知或未实测时按不可用处理。

### 5.4 服务端模型解析

```ts
resolveMarketing2Model(
  userId: string,
  modelId: string,
  requiredCapabilities: string[]
)
```

校验顺序：

1. `modelId` 属于当前用户。
2. 模型处于启用状态。
3. 实测状态满足当前能力要求。
4. 能力标签满足当前步骤要求。
5. 服务端解密密钥并创建对应 Adapter。

错误码：`MODEL_NOT_FOUND`、`MODEL_DISABLED`、`MODEL_CAPABILITY_MISSING`、`MODEL_TEST_REQUIRED`、`MODEL_TEST_FAILED`。

## 6. 数据模型改造

### 6.1 MarketingTask

增加可空或带默认值字段：

```text
workflowKey       String?
workflowVersion   Int      @default(1)
currentStep       String?
taskVersion       Int      @default(1)
awaitingReview    Boolean  @default(false)
```

`module` 固定使用 `marketing2-image-detail`，与旧 `copywriting/translate/seo/geo/insight` 模块区分。

### 6.2 MarketingTaskItem

增加：

```text
stepKey       String?
itemVersion   Int      @default(1)
idempotencyKey String?
```

Item 状态统一为：

```text
pending/running/awaiting_review/completed/failed/skipped/cancelled
```

建议 Item 类型：

```text
material_validate
background_cleanup
visual_analysis
prompt_planning
main_image:<index>
detail_page:<index>
quality_check:<assetId>
repair:<assetId>:<issueType>
```

### 6.3 Asset 版本关系

为 `Asset` 增加稳定追踪字段：

```text
marketingTaskId String?
parentAssetId   String?
revision        Int      @default(1)
derivedReason   String?
stepKey         String?
```

`parentAssetId` 用于原图、净化图、生成图和返修图的派生关系；原图删除策略与任务删除策略分离。

### 6.4 事件

事件类型至少包含：

```text
workflow_created
step_started
step_completed
step_failed
step_approved
step_skipped
item_retried
task_completed
task_failed
```

事件 payload 只保存脱敏摘要、耗时、错误码、requestId、版本号和结果引用。

## 7. API 契约

### 7.1 工作流和任务列表

```text
GET /api/marketing2/workflows
GET /api/marketing2/runs?status=draft,awaiting_review&workflowKey=...&cursor=...&limit=20
```

列表查询必须按当前用户过滤，并返回卡片状态所需的最小摘要。

### 7.2 创建和保存草稿

```text
POST  /api/marketing2/runs
PATCH /api/marketing2/runs/:id
GET   /api/marketing2/runs/:id
```

创建接口只创建草稿，不自动执行。请求：

```ts
type CreateMarketing2RunRequest = {
  workflowKey: string;
  workflowVersion?: number;
  input: unknown;
  stepModels: Record<string, string>;
};
```

服务端根据 `workflowKey` 选择 Schema，并校验模型 ID。PATCH 必须携带 `expectedVersion`，只允许更新当前阶段允许编辑的字段。

### 7.3 执行、审批和重试

```text
POST /api/marketing2/runs/:id/steps/:stepKey/execute
POST /api/marketing2/runs/:id/steps/:stepKey/approve
POST /api/marketing2/runs/:id/items/:itemId/retry
```

所有写操作要求：

- 请求头携带 `Idempotency-Key`。
- Body 携带 `expectedVersion`。
- 服务端事务检查任务归属、步骤依赖、版本和当前状态。
- 重复请求返回第一次请求的结果，不重复创建 Item 或 Asset。
- 并发版本冲突返回 `VERSION_CONFLICT`，前端重新拉取详情。

### 7.4 导出

```text
POST /api/marketing2/runs/:id/export
```

支持 JSON、Markdown、提示词包、质检报告和图片资产清单。导出文件创建 `Asset`，并关联原任务 ID。

## 8. 状态机与并发控制

### 8.1 任务状态

```text
draft
  -> running_step
  -> awaiting_review
  -> running_step
  -> completed

running_step -> partial_failed -> retry / continue
running_step -> failed
```

服务端是唯一状态机。前端不能通过路由或本地状态直接跳步。

### 8.2 步骤推进规则

- 执行前检查所有 `dependsOn`。
- 底图净化允许记录原因后 `skipped`。
- 视觉识别、提示词策划和质检必须完成或通过人工豁免。
- 审批保存用户编辑后的合法结果，并生成新结果版本。
- 下游失败不清空上游已确认结果。

### 8.3 幂等和锁

- 任务更新使用 `taskVersion` 乐观锁。
- Item 执行使用 `idempotencyKey` 唯一约束。
- Worker 继续使用租约，API 触发执行时不得绕过 Item 领取逻辑。
- 审批和重试都在事务内更新状态、结果和事件。

## 9. 执行器设计

建议新增：

```text
src/lib/marketing2/workflow-registry.ts
src/lib/marketing2/run-service.ts
src/lib/marketing2/model-routing.ts
src/lib/marketing2/step-executors.ts
src/lib/marketing2/schemas.ts
src/lib/marketing2/asset-versioning.ts
```

执行器职责：

- `material_validate`：输入校验和风险提示。
- `background_cleanup`：调用图片编辑 Adapter。
- `visual_analysis`：调用视觉文本模型，输出事实和外观锁定描述。
- `prompt_planning`：调用结构化文本模型，生成主图和详情页规划。
- `main_image/detail_page`：调用图片生成 Adapter，并保存资产版本。
- `quality_check`：调用视觉模型，输出结构化十项质检。
- `repair`：根据问题类型调用图片编辑 Adapter，创建派生资产。

现有图片接口不能直接接收浏览器传入的完整配置。营销助手2必须通过服务端模型解析后调用受保护 Adapter，并附带当前用户和任务归属。

## 11. 分阶段开发计划

### Phase 0：契约、迁移和 Mock

- 冻结五个 `workflowKey`、步骤 key、输入输出 Schema 和错误码。
- 冻结任务和 Item 状态机、版本号和幂等策略。
- 设计 `ModelConfig` 图片能力扩展和旧图片配置迁移。
- 扩展 connection/json/vision/imageGeneration/imageEditing/referenceImage 测试 Mock。
- 评审 Asset 版本关系和存量迁移策略。

退出条件：Schema、迁移设计、能力矩阵、状态机和 Mock 均通过评审。

### Phase 1：卡片中心和任务列表

- 实现工作流注册表和卡片 API。
- 实现 `/marketing2` 卡片网格。
- 实现任务列表、最近任务、继续任务和历史导入。
- 实现无模型、无权限和工作流不可用状态。

退出条件：五张卡片和任务状态均来自服务端契约。

### Phase 2：草稿和素材阶段

- 实现创建草稿、PATCH 自动保存和详情恢复。
- 实现版本号、幂等键和任务归属校验。
- 实现图片上传、资源库选择、图片替换和素材校验。

退出条件：刷新、重复保存、并发保存均不会丢失或覆盖新版本。

### Phase 3：底图净化和视觉策划

- 完成图片能力迁移和安全 Adapter。
- 实现底图净化、接受、重试、跳过和派生资产。
- 实现视觉识别、OCR、事实状态和风险结果。
- 实现提示词策划、Schema 校验、用户编辑和审批。

退出条件：模型选择只来自设置，所有结果可审计，阶段状态可恢复。

### Phase 4：批量生图和资产版本

- 实现主图/详情页数量上限和批次拆分。
- 实现并发队列、单项重试、暂停和恢复。
- 实现图片命名清洗、冲突处理和 Asset 派生关系。
- 保存每张图片的模型快照、提示词、参考图和步骤版本。

退出条件：重复点击不产生重复资产，部分失败可单项重试。

### Phase 5：质检、返修和复检

- 实现 `QualityCheckResult` Schema 和十项检查。
- 实现失败阻断、警告确认和人工豁免。
- 实现四类返修指令和新版本资产。
- 实现返修后的复检和质检报告导出。

退出条件：质检、返修、复检、人工豁免和事件记录完整闭环。

### Phase 6：发布门禁

- 完成单元、API、E2E 和多视口测试。
- 完成空库迁移、存量迁移、回滚演练和图片配置迁移演练。
- 保留旧营销助手入口，先灰度开放营销助手2。
- 观察任务成功率、部分失败率、模型错误率、重复执行率和导出失败率。

## 12. 测试计划

### 12.1 单元测试

- 工作流注册表和五张卡片契约。
- 每张卡片的输入输出 Schema。
- 模型能力过滤和实测状态门禁。
- 状态转换、依赖校验、版本冲突和幂等键。
- 批次拆分、数量上限和文件名清洗。
- 质检结果聚合和完成门禁。
- Asset 父子版本关系。

### 12.2 API 测试

- 越权任务、模型、资产和非法 `workflowKey`。
- 停用、未实测、能力不足模型拦截。
- 前端传入 API Key、Base URL、完整 `config` 时拒绝。
- 创建、PATCH 草稿、列表筛选、游标分页和详情恢复。
- 重复执行、重复审批、重复重试和版本冲突。
- 上传伪装文件、超大文件、空图片。
- 上游超时、429、5xx、无效 JSON 和部分失败。

### 12.3 E2E 测试

- 从卡片中心进入五种工作流。
- 创建草稿、刷新恢复、继续任务和历史导入。
- 每个步骤选择不同模型并验证任务快照。
- 批量生图部分失败后单张重试。
- 质检失败、人工豁免、返修和复检。
- 原图、净化图和返修图均保留版本关系。

### 12.4 视口和无障碍

至少覆盖 `1440×900`、`1024×768`、`390×844`，检查横向溢出、长文本遮挡、图片预览、加载、空状态、错误状态和键盘操作。

## 13. 数据迁移、回滚和隐私

- 只增加可空或有默认值字段，不删除旧营销列。
- 新字段迁移后旧任务仍可查询和导出。
- 图片配置迁移必须用户显式确认，失败不删除旧配置。
- 新入口异常时可隐藏卡片或关闭路由，不删除任务和图片资产。
- 回滚不得自动删除用户文件。
- 原始产品图、模型输入、生成图和质检结果按照项目现有用户归属规则隔离。
- 日志只保存 requestId、错误码、耗时和脱敏摘要，不记录 API Key、完整图片 Base64 或完整敏感提示词。

## 14. 风险和退出条件

| 风险 | 处理方式 | 阻塞级别 |
|---|---|---|
| 图片模型无法安全迁移到服务端 | 暂停阶段二和阶段四，只开放文字策划 | P1 |
| 新图片能力无法实测 | 从选择器隐藏对应模型，不降级伪装可用 | P1 |
| 任务并发状态不一致 | 未完成幂等和版本锁前不得开放执行 | P1 |
| Asset 版本无法追溯 | 未完成迁移前不得开放返修覆盖流程 | P1 |
| 质检结果无法结构化 | 只能展示人工检查，不得标记自动通过 | P2 |
