# 营销助手2开发实施文档 V3

## 1. 文档信息

- **文档状态**：V3 实施方案，待技术评审
- **对应交互文档**：`营销助手2_交互设计文档V3.md`
- **基础需求**：`设计1.md`
- **前序版本**：`营销助手2_开发实施文档V2.md`
- **目标入口**：`/marketing2`
- **核心改造**：将 V2 的五张并列工作流卡片收敛为一个“主图详情页全自动生成”入口，并实现一个任务贯穿五步的连续向导。

## 2. 实施目标

1. 营销助手2首页只展示一个可创建任务的主流程卡片。
2. 原底图净化、提示词策划、批量生图、质检返修能力迁入主流程内部。
3. 第一步准备产品图和第二步可选底图精修在同一个页面完成。
4. 第三步一次完成产品视觉识别与整套提示词生成。
5. 第四步按照提示词逐张生成主图和详情页。
6. 第五步逐张质检，不合格图片局部返修并自动复检。
7. 所有模型均从设置中的服务端模型库读取。
8. 每个模型下拉框只控制当前页面、当前图片或当前返修任务，不与其他页面联动。
9. 上游修改后将下游结果标记为失效，但保留全部历史版本。
10. 旧营销助手和已创建的 V2 营销助手2任务继续可查询，不做破坏性删除。
11. 图片生成支持任务内可配置并发，默认保守执行，并受模型服务与系统全局限流共同约束。

## 3. 当前基线与 V3 改造边界

当前代码已经具备：

- 五工作流注册表和卡片中心。
- `MarketingTask`、`MarketingTaskItem`、`MarketingTaskEvent` 异步任务体系。
- 草稿保存、版本锁、幂等键、暂停、重试和导出。
- 服务端模型配置和图片能力实测。
- 素材校验、底图净化、视觉识别、提示词策划、批量生图、质检返修执行器。
- Asset 父子版本关系。

V3 以交互收敛和任务编排调整为主，不重新实现已有模型 Adapter、文件存储、Worker 和 Asset 基础设施。

### 3.1 保留的后端步骤 key

为兼容现有数据，后端继续保留以下 Item/步骤 key：

```text
material_validate
background_cleanup
visual_analysis
prompt_planning
batch_generation
quality_repair
```

V3 UI 将其投影为五个逻辑步骤：

| V3 逻辑步骤 | 后端步骤/Item | UI 页面 |
|---|---|---|
| 1. 准备产品图 | `material_validate` | 产品准备页 |
| 2. 底图精修（可选） | `background_cleanup` | 与产品准备页同屏 |
| 3. 提示词策划 | `visual_analysis` + `prompt_planning` | 提示词策划页 |
| 4. 逐张生图 | `main_image:*` + `detail_page:*` | 图片生成页 |
| 5. 质检返修 | `quality_check:*` + `repair:*` | 质检返修页 |

不通过重命名数据库步骤来实现 UI 合并，避免历史任务迁移和 Worker 兼容成本。

## 6. 页面独立模型选择

### 6.1 模型选择数据结构

`MarketingTask.stepModels` 从简单的步骤字符串映射升级为 V3 结构。数据库字段仍使用 JSON，不需要新增列：

```ts
type Marketing2V3ModelSelections = {
  backgroundCleanup?: string;
  visualAnalysis?: string;
  promptGeneration?: string;
  imageGeneration: {
    items: Record<string, string>;
  };
  quality: {
    items: Record<string, string>;
  };
  repair: {
    items: Record<string, string>;
  };
};
```

键约定：

```text
imageGeneration.items[planItemId]
quality.items[assetId]
repair.items[repairRequestId]
```

### 6.2 独立保存规则

1. 第二步图片模型只写 `backgroundCleanup`。
2. 第三步两个文本模型分别写 `visualAnalysis` 和 `promptGeneration`。
3. 第四步每个计划项都写入独立 `planItemId -> modelId`。
4. 第五步每张图片独立写入 `assetId -> qualityModelId`。
5. 每次返修写入独立 `repairRequestId -> repairModelId`。
6. 修改任意键不能改变其他键。
7. 页面刷新后从任务 `stepModels` 恢复本页选择。
8. 下拉框仅展示当前用户在“设置”中保存、启用且已通过实测的模型；客户端不得传入模型名称、Base URL、API Key 或临时模型配置。
9. 下拉框变更以 `modelId` 为唯一值即时保存；执行动作再次以服务端设置库校验，避免已停用、越权或能力变化的模型被调用。

模型选择写入接口：

```text
PATCH /api/marketing2/runs/:id/model-selections
```

```ts
type PatchModelSelectionsRequest = {
  expectedVersion: number;
  changes: Array<{
    scopeKey:
      | 'backgroundCleanup'
      | 'visualAnalysis'
      | 'promptGeneration'
      | `imageGeneration:${string}`
      | `quality:${string}`
      | `repair:${string}`;
    modelId: string;
  }>;
};
```

服务端在一个事务中校验任务归属、scope 对应的计划项/图片/返修请求是否存在，以及模型是否来自该用户设置库、处于启用且实测通过状态并满足当前能力要求。校验通过后只更新对应键、递增任务版本并写入事件；前端可在 400ms 防抖后自动提交。批量设置由前端展开为多个独立 `changes`，不保存共享默认值或继承关系。

### 6.3 批量设置不是联动

第四步和第五步可以提供“批量设置模型”。该操作只把模型 ID 一次写入当前未锁定项目的独立键，不建立持续继承关系。

例如用户给全部主图批量设置模型 A 后，再把主图 03 改为模型 B：

```text
主图 01 -> A
主图 02 -> A
主图 03 -> B
主图 04 -> A
```

再次批量设置不能覆盖已生成项目；未生成项目中的单项修改也始终是独立保存值。

### 6.4 模型快照

每次创建 Item 时立即解析当前模型并写入不可变快照：

```ts
type ItemModelSnapshot = {
  id: string;
  name: string;
  provider: string;
  model: string;
  capabilities: string[];
  testedAt?: string;
};
```

快照在 Item 创建时固定写入 `MarketingTaskItem.input.modelSnapshot`，不保存 API Key。由该 Item 产出的 Asset 固定写入 `Asset.parameters.marketing2.modelSnapshot`，并补充 `taskItemId`、`planItemId`（如有）和 `promptRevision`。不得将快照散落在可变结果 JSON 中；模型设置随后改变不会回写既有 Item 或 Asset。

## 7. 第一步与第二步实施

### 7.1 输入 Schema

```ts
type ProductPreparationInput = {
  productImages: string[];
  primaryImageId: string;
  cleanupEnabled: boolean;
  cleanupModelId?: string;
};
```

校验：

- 产品图 1-5 张。
- `primaryImageId` 必须属于 `productImages`。
- 开启精修时 `cleanupModelId` 必填。
- 关闭精修时忽略旧的 `cleanupModelId`，但历史执行记录不删除。

### 7.2 同屏状态机

```text
产品图未完成
  -> 产品图已保存
  -> cleanupEnabled = false
       -> material_validate approved
       -> background_cleanup skipped
       -> 进入第三步
  -> cleanupEnabled = true
       -> 选择模型
       -> 执行精修
       -> 待确认
       -> 接受底图 / 重新生成 / 放弃并使用原图
```

### 7.3 固定精修提示词

精修提示词保存在服务端常量中，例如：

```text
src/lib/marketing2-v3/prompts/background-cleanup.ts
```

API 不接收客户端传入的精修 prompt。请求体出现 `prompt/systemPrompt/instructionOverride` 时返回 `FORBIDDEN_FIELDS`。

执行输入包含：主参考图、补充视角图、固定提示词和所选模型 ID。首期只输出一张干净底图。

### 7.4 底图接受状态

`background_cleanup` Item 完成不等于已经进入第三步。用户接受结果后写入：

```ts
stepResults.background_cleanup = {
  status: 'approved';
  revision: number;
  acceptedAssetId: string;
  sourceImageRevision: number;
};
```

放弃精修时写入 `skipped` 和原因，第三步改用原始主参考图。

## 8. 第三步提示词策划实施

### 8.1 页面输入

使用 V3 交互文档定义的结构化字段：平台、语言、数量、比例、产品名称、品牌、卖点、参数、人群、场景、定位、风格、禁止内容和其他要求。

空值或“依产品特性生成”在服务端转为 `auto`，不能在客户端写死 5 张主图或 8 页详情页。

服务端以 Zod 为最终边界校验数量：手动主图为 `1-10` 张、手动详情页为 `1-20` 页，二者合计不超过 `30`。`auto` 的模型输出也必须满足相同上限；超出时仅允许基于固定模板做一次限量修正，仍不合格则返回 `PLANNING_OUTPUT_LIMIT_EXCEEDED`，且不创建任何生图 Item。前端只做同步提示，不能绕过服务端限制。

### 8.2 两个独立模型

页面必须同时显示：

```text
产品视觉识别文本模型 -> visualAnalysis
提示词生成文本模型   -> promptGeneration
```

两个选择器不提供“跟随”开关。允许选择同一个模型，但数据仍分别保存。

### 8.3 单页编排

用户点击“生成整套提示词”后，服务端执行：

```text
visual_analysis
      ↓ 成功
prompt_planning
      ↓ 成功
第三步 awaiting_review
```

前端把两次模型调用展示为同一页面的两个子状态，不要求用户在中间审批视觉识别结果。视觉识别失败时不创建提示词生成 Item。

实现采用显式依赖而非 Worker 内部临时串行：提交动作在同一事务内创建 `visual_analysis` Item（`pending`）和 `prompt_planning` Item（`blocked`），后者在输入中固定 `dependencyItemId` 与同一次用户输入版本。视觉识别成功且输出 Schema 校验通过后，Worker 在事务中将对应的提示词 Item 从 `blocked` 释放为 `pending`；视觉识别失败时提示词 Item 保持 `blocked`，重试视觉识别会复用并释放该 Item，不创建重复计划。只有提示词生成成功后，页面才进入 `awaiting_review`。

### 8.4 固定系统规则

产品锁定、真实性、主图、详情页、视觉风格、文字排版和输出格式规则保存在服务端版本化 Prompt 模板中。客户端只提交结构化用户输入和模型 ID。

建议文件：

```text
src/lib/marketing2-v3/prompts/product-analysis.ts
src/lib/marketing2-v3/prompts/prompt-planning.ts
```

### 8.5 结果 Schema

```ts
type PromptPlanningResultV3 = {
  productAnchor: string;
  confirmedFacts: MarketingFact[];
  inferredFacts: MarketingFact[];
  pendingFacts: MarketingFact[];
  plans: Array<{
    id: string;
    kind: 'main_image' | 'detail_page';
    index: number;
    keyword: string;
    responsibility: string;
    ratio: string;
    prompt: string;
  }>;
};
```

每条 `prompt` 必须以固定产品参考约束开头并包含 `productAnchor`。服务端 Schema 校验数量、索引、比例、提示词长度和主图/详情页上限。

用户编辑时只允许字段级 Patch。修改后的计划生成新 `promptRevision`，旧版本保留。

## 9. 第四步逐张生图实施

### 9.1 计划项与模型选择

第三步审批后，为每条 plan 生成稳定的 `planItemId`。第四步页面根据 `planItemId` 保存图片模型。

未选择模型的计划项不能执行。模型必须满足：

```text
imageGeneration = true
referenceImage = true
testStatus = passed
```

### 9.2 单项生成 API

```text
POST /api/marketing2/runs/:id/generation-items/:planItemId/execute
```

请求：

```ts
type ExecuteGenerationItemRequest = {
  expectedVersion: number;
  promptRevision: number;
  textMode: 'with_text' | 'without_text';
};
```

请求头必须包含 `Idempotency-Key`。服务端从 `imageGeneration.items[planItemId]` 读取模型 ID，并重新从当前用户设置库校验模型能力、启用状态和实测状态。

### 9.3 批量生成与任务内并发

```text
POST /api/marketing2/runs/:id/generation-items/execute-batch
```

```ts
type ExecuteGenerationBatchRequest = {
  expectedVersion: number;
  promptRevision: number;
  concurrency: 1 | 2 | 3 | 4 | 5;
};
```

批量动作只为未完成项创建任务，并将本次任务的 `generationConcurrency` 保存到 `stepResults.batch_generation`；默认值为 `1`，可选范围为 `1-5`。每条计划项仍保留稳定 `sequence`、独立模型、状态、结果和重试记录。

Worker 领取图片 Item 时按 `sequence` 排序，并在事务内取得该 task 的 PostgreSQL advisory lock，统计该 task 当前 `running` 的生图 Item；只有运行数小于 `generationConcurrency` 才可领取下一项。这样多个 Worker 同时轮询同一任务也不会突破任务内并发上限。全局 Worker 并发、供应商限流和单模型限流仍是额外上限，实际并发取最小值。

暂停后不再领取下一项，已经运行的 Item 允许完成。

### 9.4 图片来源

参考图优先级：

1. 用户接受的精修底图。
2. 原始主参考图。
3. 其余原始图片作为补充视角。

每个 Item 输入保存参考资产 ID、promptRevision、比例、页面职责、模型快照和文字模式。

### 9.5 生成结果

- 每次生成创建新 Asset。
- 重新生成增加 revision，不覆盖旧 Asset。
- 用户“接受”某版本后，设置为当前 planItemId 的有效资产。
- 提示词只能回到第三步编辑，第四步不直接修改提示词正文。

`stepResults.batch_generation` 是每条计划项当前图片状态的唯一业务来源：

```ts
type GenerationPlanStateV3 = {
  sequence: number;
  promptRevision: number;
  modelId?: string;
  activeAssetId?: string;
  activeAssetRevision?: number;
  status: 'pending' | 'running' | 'awaiting_review' | 'accepted' | 'skipped' | 'failed';
  stale: boolean;
};
```

重新生成或返修只替换对应计划项的 `activeAssetId` 和 revision；旧 Asset、旧质检及旧返修记录保留在历史中，不能再作为当前完成门禁依据。

### 9.6 完成门槛

每个 planItemId 必须处于：

- 已接受；或
- 用户填写原因后已跳过。

失败、待生成和生成后未确认的项目不能进入第五步。

## 10. 第五步质检返修实施

### 10.1 逐图质检模型

每个已接受 Asset 保存独立质检模型：

```text
quality.items[assetId] = modelId
```

质检模型需要 `vision` 和 `jsonMode`。未选择模型的图片不能质检。

### 10.2 质检 API

```text
POST /api/marketing2/runs/:id/quality-items/:assetId/execute
POST /api/marketing2/runs/:id/quality-items/execute-all
```

执行全部只是为每张图片创建独立 Item；每个 Item 固化自己的 modelId 和模型快照。

### 10.3 质检结果

沿用结构化十项结果：

```ts
type QualityCheckResult = {
  assetId: string;
  assetRevision: number;
  overallStatus: 'passed' | 'needs_repair' | 'needs_review';
  items: QualityCheckItem[];
  blockingIssues: string[];
};
```

质检结果必须绑定具体 Asset revision。图片重新生成或返修后，旧质检结果自动标记为 stale。

### 10.4 独立返修模型与请求生命周期

选择返修类型后，前端先创建返修请求，不立即调用模型：

```text
POST  /api/marketing2/runs/:id/repairs
PATCH /api/marketing2/runs/:id/repairs/:repairRequestId
POST  /api/marketing2/runs/:id/repairs/:repairRequestId/execute
```

创建接口以 `assetId`、`assetRevision`、`issueType` 与 `expectedVersion` 创建 `MarketingTaskItem`，其 Item ID 即 `repairRequestId`，初始为 `draft`；用户通过模型选择接口写入 `repair.items[repairRequestId]`。请求在 `draft` 或 `failed` 状态可修改返修类型和模型；执行后依次进入 `pending -> running -> awaiting_review -> accepted`，失败进入 `failed`，可在同一请求上重试回到 `pending`。每次状态变化写入事件，并永久记录问题类型、所选模型快照、源 Asset revision、创建时间和操作者。

执行请求只允许包含 `expectedVersion` 和幂等键。服务端从返修请求与设置库读取 asset、issueType、modelId，并按 issueType 选择四类固定返修 prompt，客户端不能覆盖。

返修成功后：

1. 创建父资产为原图的新 Asset revision。
2. 将新版本设为当前有效图片。
3. 为新版本创建待执行质检项。
4. 保留原图、原质检和原返修记录。

### 10.5 完成门禁

- 所有当前有效图片质检通过；或
- warning 已人工确认；或
- failed 已返修通过；或
- 用户填写原因后执行人工豁免。

人工豁免写入事件，包含 assetId、问题、原因、时间和用户 ID。

## 11. 上下游失效机制

### 11.1 步骤结果结构

`stepResults` 中每个步骤使用版本化包装：

```ts
type VersionedStepResult<T> = {
  revision: number;
  sourceRevision: number;
  status: 'draft' | 'awaiting_review' | 'approved' | 'skipped';
  stale: boolean;
  approvedAt?: string;
  result: T;
};
```

### 11.2 失效规则

| 修改 | 服务端动作 |
|---|---|
| 替换主参考图 | 标记精修、提示词、生成图当前引用、质检为 stale |
| 增删补充视角图 | 标记视觉识别、提示词、生成图当前引用、质检为 stale |
| 开关精修或更换底图 | 标记提示词、生成图当前引用、质检为 stale |
| 修改产品参数/卖点 | 标记提示词、生成图当前引用、质检为 stale |
| 修改单条提示词 | 只标记对应生成项及质检为 stale |
| 重新生成图片 | 只标记该图片旧质检为 stale |

`stale` 结果继续可查看和导出历史，但不能作为当前步骤完成依据。

失效处理必须同步更新受影响 `GenerationPlanStateV3` 的 `stale`、`activeAssetId`/`activeAssetRevision` 和状态；第五步只读取每条计划项当前有效 Asset 对应的质检状态，不能按 Asset 列表推断当前图片。

### 11.3 失效确认

修改会影响下游时，PATCH API 返回影响列表。前端弹出确认对话框，用户确认后携带 `confirmInvalidation: true` 再次提交。

- 所有计划项接受/跳过：进入质检页。
- 所有当前有效图片通过质检或人工豁免：任务 completed。

## 17. 数据兼容与回滚

- V3 不删除 V2 工作流定义、任务、Item、事件和 Asset。
- 任务详情路由先读取 `workflowVersion`：`workflowVersion < 3` 固定加载 `Marketing2WorkflowRunnerV2`，`workflowVersion >= 3` 加载 `WorkflowWizardV3`；不建设混合兼容视图。
- V3 新建任务固定 `workflowVersion = 3`。
- V2 的 `stepModels: Record<string, string>` 仅由 V2 运行器读取，历史任务不在打开或保存时自动转换；只有显式迁移方案获批后才允许写入 V3 结构。
- 回滚 V3 时恢复五卡片展示即可，V3 JSON 字段不会阻止旧代码读取基础任务。
- 回滚不得删除用户图片和历史结果。

## 18. 风险与处理

| 风险 | 处理方式 | 级别 |
|---|---|---|
| UI 五步与后端六步骤不一致 | 使用固定投影层，不改历史 step key | P1 |
| 模型批量设置意外联动 | 批量操作写入独立项，不保存引用关系 | P1 |
| 上游修改继续使用旧图片 | 服务端 stale 门禁，不依赖前端提醒 | P1 |
| 第三步两个模型自动串行中途失败 | 显式依赖 Item；视觉识别成功可保留，重试只释放同一提示词 Item | P1 |
| 批量生图突破用户设置并发 | task advisory lock + 运行数计数，实际并发取任务、全局、供应商限流最小值 | P1 |
| V2 历史任务无法打开 | 保留注册表定义和旧运行器 | P1 |
| 固定 prompt 被客户端修改 | 服务端常量并拒绝 override 字段 | P1 |
