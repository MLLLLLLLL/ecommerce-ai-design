# 营销助手2开发实施文档

## 1. 文档信息

- **文档状态**：方案阶段，待评审后实施
- **目标入口**：`/marketing2`
- **对应设计**：`营销助手2_交互设计文档.md`
- **基础文档**：`电商主图 & 详情页 AI 全自动化生成工作流.md`
- **实施原则**：先冻结契约，再分阶段实现；不影响旧营销助手和通用工作流。

## 2. 当前代码基线与问题

### 2.1 已有能力

- `src/app/(dashboard)/marketing2/page.tsx` 已有入口，但目前为占位页面。
- `src/app/api/model-configs` 已提供服务端多文本模型配置读取和保存。
- `ModelConfig` 已有 `vision`、`jsonMode`、`ocr`、`imageGeneration` 能力标签。
- `MarketingTask`、`MarketingTaskItem`、`MarketingTaskEvent` 已具备任务、子任务、重试和事件基础设施。
- 旧营销模块已经包含产品分析、文案、主图提示词和详情页提示词引擎。

### 2.2 必须先处理的问题

1. 营销助手2不能继续使用占位页面。
2. 现有图片生成接口接收完整 `config`，需要改为只接受模型 ID 或由营销助手2专用服务端执行器调用。
3. 文本模型和图片模型目前存在不同配置链路，需要统一“设置模型目录”和能力校验。
4. `ModelCapabilities.imageGeneration` 还不足以区分文生图、图生图、参考图和图片编辑。
5. 现有任务模块字段需要增加工作流标识、步骤状态和人工确认状态。

## 3. 推荐总体架构

```text
营销助手2卡片中心
        ↓ workflowKey
工作流运行页
        ↓
Marketing2 Workflow Registry
        ↓
MarketingTask + MarketingTaskItem + MarketingTaskEvent
        ↓
步骤执行器
        ↓
模型解析服务 -> ModelConfig -> 对应 AI Adapter
        ↓
图片存储 / Asset / 任务结果
```

营销助手2采用业务工作流运行器，不直接把通用无限画布作为首期用户界面。后续可以抽取公共节点执行能力，但本期优先保证营销业务的步骤确认、模型路由和结果追踪。

## 4. 模型配置与安全改造

### 4.1 统一模型目录

以服务端 `ModelConfig` 作为营销助手2唯一模型来源。前端只读取安全摘要：

```ts
type Marketing2ModelSummary = {
  id: string;
  name: string;
  provider: string;
  model: string;
  capabilities: ModelCapabilities;
  isActive: boolean;
  testStatus?: string | null;
  lastTestedAt?: string | null;
};
```

不向浏览器返回 API Key。任务请求只提交 `modelId`。

### 4.2 能力字段扩展

在现有能力基础上增加图片处理细分能力，建议使用兼容扩展：

```ts
interface ModelCapabilities {
  vision: boolean;
  jsonMode: boolean;
  ocr: boolean;
  imageGeneration: boolean;
  imageEditing: boolean;
  referenceImage: boolean;
}
```

如果底层供应商无法准确实测某项能力，必须标记为不可用，不能仅根据模型名称推断为可用。

### 4.3 服务端解析规则

新增统一解析函数，例如：

```ts
resolveMarketing2Model(userId, modelId, requiredCapabilities)
```

校验顺序：

1. 模型 ID 存在且属于当前用户。
2. 模型处于启用状态。
3. 模型实测状态满足工作流要求。
4. 能力标签满足当前步骤要求。
5. 服务端解密密钥并创建运行时 Adapter。

错误统一返回稳定错误码，例如：

- `MODEL_NOT_FOUND`
- `MODEL_DISABLED`
- `MODEL_CAPABILITY_MISSING`
- `MODEL_TEST_REQUIRED`
- `MODEL_TEST_FAILED`

## 5. 数据模型改造

### 5.1 MarketingTask 增量字段

建议在现有 `MarketingTask` 中增加：

```text
workflowKey       String?
workflowVersion   Int      @default(1)
currentStep       String?
awaitingReview    Boolean  @default(false)
```

现有 `module` 可继续使用 `marketing2-image-detail` 作为模块值，避免与旧的文案、翻译、SEO、GEO 模块混淆。

### 5.2 MarketingTaskItem 扩展

每个工作流步骤或图片批次作为一个 Item：

```text
kind       String
stepKey    String?
role       String?
modelId    String?
dependsOn  String?
input      Json?
result     Json?
```

建议的 `kind`：

```text
material_validate
background_cleanup
visual_analysis
prompt_planning
main_image:<index>
detail_page:<index>
quality_check:<assetId>
repair:<assetId>:<issueType>
```

`modelId` 保存所选模型 ID；执行后通过任务快照记录模型名称、提供商、实际模型名和能力，不保存密钥。

### 5.3 事件记录

使用 `MarketingTaskEvent` 记录：

```text
workflow_created
step_started
step_completed
step_failed
step_approved
step_skipped
item_retried
task_completed
```

事件 payload 只保存脱敏摘要、耗时、错误码、requestId 和结果引用。

## 6. API 设计

### 6.1 工作流定义

```text
GET /api/marketing2/workflows
```

返回静态注册表中的卡片信息：工作流 key、标题、描述、输入要求、输出、首选能力和版本。

### 6.2 创建运行任务

```text
POST /api/marketing2/runs
```

请求只包含业务输入和步骤模型选择：

```ts
type CreateMarketing2RunRequest = {
  workflowKey: string;
  input: Marketing2Input;
  stepModels: Record<string, string>;
};
```

服务端创建草稿任务、验证第一阶段模型选择，并生成步骤 Items。

### 6.3 执行步骤

```text
POST /api/marketing2/runs/:id/steps/:stepKey/execute
```

执行要求：

- 校验前置步骤已完成或被允许跳过。
- 重新按当前用户解析模型。
- 只执行当前步骤及必要的失败子项。
- 成功后写入结果并将任务置为 `awaitingReview`。
- 不自动覆盖历史版本。

### 6.4 审批与继续

```text
POST /api/marketing2/runs/:id/steps/:stepKey/approve
```

审批请求包含用户编辑后的结果或确认标记。服务端校验结果结构后推进到下一步骤。

### 6.5 查询、重试和导出

```text
GET  /api/marketing2/runs/:id
POST /api/marketing2/runs/:id/items/:itemId/retry
POST /api/marketing2/runs/:id/export
```

导出内容包括提示词、质检报告、任务 JSON、Markdown 和最终图片资产引用。

## 9. 分阶段实施计划

### Phase 0：契约和模型能力冻结

- 冻结卡片 `workflowKey`、五阶段 `stepKey` 和任务状态。
- 冻结输入、结果、事件和错误码 Schema。
- 明确服务端模型配置作为唯一来源。
- 增加图片编辑、参考图能力定义。
- 准备模型 Mock：成功、超时、429、5xx、能力不足、无效 JSON。

退出条件：TypeScript 类型、Zod Schema、模型能力矩阵通过评审。

### Phase 1：工作流卡片中心

- 实现 `/marketing2` 卡片网格。
- 实现卡片状态、最近任务和继续任务入口。
- 实现 `workflowKey` 路由和不存在工作流的空状态。

退出条件：五张首期卡片可以正确进入对应工作流。

### Phase 2：工作流运行器与素材阶段

- 实现运行任务创建、草稿保存和恢复。
- 实现步骤栏、模型选择器和通用执行状态。
- 实现素材上传、资源库选择和参数表单。
- 实现素材校验 Item。

退出条件：用户可创建任务、刷新页面恢复草稿，并完成第一阶段确认。

### Phase 3：底图净化与视觉策划

- 接入图片编辑模型和底图前后对比。
- 接入视觉分析、可见文字识别和风险输出。
- 接入主图/详情页规划和逐张提示词生成。
- 支持用户编辑结果后审批。

退出条件：阶段二可跳过，阶段三结果可编辑、可保存、可重试。

### Phase 4：分批生图与资产归档

- 实现主图和详情页批次拆分。
- 实现单张 Item、批次进度和单项重试。
- 实现比例、参考图、命名规则和资产入库。
- 保存每张图片的模型快照和提示词。

退出条件：一个批次部分失败时，成功图片保留且失败图片可单独重试。

### Phase 5：质检与返修闭环

- 实现十项质检结构化结果。
- 实现四类固定返修指令。
- 原图与返修图使用版本关系关联，不覆盖原图。
- 支持质检报告导出。

退出条件：质检、返修、复检形成完整闭环。

### Phase 6：质量门禁与发布

- 补齐单元测试、API 测试和 Playwright 测试。
- 完成移动端和桌面端视觉检查。
- 完成数据库迁移、空库迁移和存量数据验证。
- 先保留旧营销助手入口，再开放营销助手2。

## 10. 测试计划

### 10.1 单元测试

- 工作流定义注册和卡片过滤。
- 模型能力匹配和模型失效处理。
- 输入 Schema 边界和占位符规则。
- 步骤状态转换和前置依赖。
- 十项质检结果聚合。
- 文件命名和批次拆分。

### 10.2 API 测试

- 越权模型 ID、越权任务 ID。
- 停用模型和未实测模型拦截。
- 前端传入 API Key、Base URL、完整 config 时拒绝。
- 上传伪装文件、超大文件、空图片。
- 上游超时、429、5xx 和无效 JSON。
- 部分成功、单项重试和导出失败。

### 10.3 E2E 测试

- 卡片中心进入五种工作流。
- 创建任务、执行当前步骤、审批并进入下一步。
- 刷新页面后恢复任务。
- 每一步切换不同模型并正确保存。
- 批量生图部分失败后单张重试。
- 质检后执行返修并保留原图。

### 10.4 视口验收

至少覆盖：

```text
1440 x 900
1024 x 768
390 x 844
```

检查横向溢出、长文本遮挡、模型选择器、图片预览、键盘操作、加载和错误状态。

## 11. 数据迁移与回滚

- 只增加可空字段或有默认值字段，不删除旧营销字段。
- 旧 `MarketingTask` 和旧接口保持可查询、可导出。
- 新工作流出现严重问题时，可隐藏卡片或关闭新入口，不删除任务和资产。
- 图片资产回滚时不得自动删除用户文件。
- 模型能力测试失败只更新测试状态，不修改 API Key。

## 12. 主要风险

| 风险 | 处理方式 |
|---|---|
| 图片模型配置仍走旧本地链路 | 先建立服务端模型解析，再接入营销助手2 |
| 不同模型能力描述不准确 | 以实测能力为准，选择器只展示可验证能力 |
| 图片生成耗时过长 | 使用现有异步 Item、轮询和单项重试 |
| 用户跳过必要步骤 | 服务端校验依赖关系，前端只做体验提示 |
| 返修覆盖原图 | 每次返修创建新版本，原图只读保留 |
| 上游返回乱码或虚构参数 | JSON Schema、待确认事实和质检步骤共同拦截 |
