# 营销助手2交互式工作流设计文档 V2

## 1. 文档信息

- **文档状态**：V2 方案，待产品与技术评审
- **适用入口**：`/marketing2`
- **V1 文档**：`营销助手2_交互设计文档.md`
- **基础文档**：`电商主图 & 详情页 AI 全自动化生成工作流.md`
- **本版本重点**：补齐工作流契约、模型路由、草稿恢复、并发控制、资产版本和质检门禁。

## 2. 产品定位

营销助手2是营销业务工作流中心，不是一次性表单，也不是首期的无限画布编辑器。用户先选择一个工作流，再按阶段完成输入、模型执行、人工确认、批量生成和质量验收。

### 2.1 产品目标

1. 点击“营销助手2”后首先进入工作流卡片中心。
2. 每张卡片对应一个有明确输入、输出和前置条件的业务工作流。
3. 文字处理模型和图片处理模型全部引用设置中已保存的模型。
4. 每个步骤可以独立选择满足能力要求的模型。
5. 每个步骤执行后进入等待确认状态，用户确认后才推进下一步。
6. 失败只影响当前步骤或当前子项，已确认的结果不被覆盖。
7. 任务可保存、恢复、审计、重试和导出。

### 2.2 非目标

- 首期不把营销助手2改造成通用画布编辑器。
- 首期不支持用户在工作流中输入 API Key、Base URL 或临时模型配置。
- 首期不允许用模型记忆替代真实参数、认证、销量、排名等事实。
- 首期不承诺所有图片供应商都支持图生图和参考图；能力不足时必须阻止执行。

## 3. 工作流卡片契约

工作流卡片不是纯 UI 数据，而是由版本化注册表驱动。每个卡片必须声明：

```ts
type WorkflowCardDefinition = {
  key: string;
  version: number;
  title: string;
  description: string;
  requiredInputs: string[];
  optionalInputs: string[];
  outputTypes: string[];
  requiredCapabilities: string[];
  steps: string[];
  importSources: string[];
};
```

### 3.1 首期卡片

| `workflowKey` | 必填输入 | 输出 | 步骤 |
|---|---|---|---|
| `marketing2-image-detail-full` | 至少 1 张产品图、产品基本信息 | 底图、策划、提示词、营销图片、质检报告 | 五阶段完整链路 |
| `marketing2-background-cleanup` | 至少 1 张产品图 | 净化底图、模型快照 | 上传/选择图片、净化、确认 |
| `marketing2-prompt-planning` | 产品图或底图、产品参数 | 外观锁定描述、主图规划、详情页规划、提示词 | 视觉识别、提示词策划、确认 |
| `marketing2-batch-generation` | 提示词或历史策划结果、参考图 | 主图/详情页图片资产 | 批次配置、生成、复核 |
| `marketing2-quality-repair` | 已生成图片 | 质检报告、返修图、复检结果 | 质检、修复、复检 |

### 3.2 独立卡片进入规则

- 进入中间工作流时，优先提供“从历史任务导入”。
- 没有历史结果时，只显示该卡片声明的最小输入，不默认假设上游数据存在。
- 导入内容必须经过对应输入 Schema 校验，不能直接把历史 JSON 当作可信数据。
- 卡片状态由任务列表和模型能力接口共同决定，不由前端静态猜测。

## 4. 工作流中心交互

### 4.1 页面布局

- 顶部：页面标题、最近任务、返回旧版营销助手入口。
- 主区域：响应式工作流卡片网格。
- 桌面端 3 列，平板端 2 列，移动端 1 列。
- 卡片整体可点击，不在卡片内部嵌套第二层卡片。
- 卡片展示名称、输入摘要、输出摘要、模型配置状态和最近运行状态。

### 4.2 卡片状态

- **可开始**：必需输入规则和模型能力均满足。
- **需要配置模型**：明确列出缺少的能力，并提供设置页返回地址。
- **继续任务**：存在当前用户的 `draft` 或 `awaiting_review` 任务。
- **有历史结果**：存在可导入的已完成任务或资产。
- **不可用**：工作流版本被禁用或依赖服务未配置。

卡片中心通过以下接口获得动态状态：

```text
GET /api/marketing2/workflows
GET /api/marketing2/runs?status=draft,awaiting_review&limit=5
```

## 5. 工作流运行页面

### 5.1 页面结构

```text
顶部：任务名称、保存状态、任务状态、返回卡片中心
左侧：阶段步骤栏、当前阶段、完成/失败/等待确认状态
中间：当前阶段表单、图片预览、结果编辑器
右侧：当前步骤模型、执行参数、运行记录和错误详情
底部：保存草稿、执行当前步骤、确认并继续、重试
```

移动端改为上下结构：步骤栏折叠为横向进度条，模型设置和运行记录位于当前内容下方。

### 5.2 通用交互状态

所有步骤统一使用：

```text
idle -> running -> awaiting_review -> approved
                         └-> failed -> retrying
```

步骤只有在 `approved` 或明确 `skipped` 后才能推进。底图净化允许 `skipped`，素材校验、视觉识别、提示词策划和质检不能无理由跳过。

## 6. 主流程五阶段

### 6.1 阶段一：素材与参数

字段分组：

- **图片**：产品图 1-5 张，支持上传、资源库选择、删除和替换。
- **平台**：淘宝/天猫、京东、抖音、小红书、亚马逊等。
- **输出**：语言、主图数量、详情页数量、比例。
- **产品**：产品名称、品牌名、核心卖点、产品参数。
- **定位**：目标人群、使用场景、价格带/定位、设计风格。
- **约束**：禁止出现、其他要求。

数量规则：

- 主图支持自动规划或手动指定，手动范围为 1-10 张。
- 详情页支持自动规划或手动指定，手动范围为 1-20 页。
- 单次任务主图和详情页合计不超过 30 个生图子项。
- 超过限制时前后端都拒绝，并定位具体字段。

执行前校验：

1. 图片服务端文件校验通过后，才写入任务输入。
2. 至少存在一张图片。
3. 关键参数为空时生成“待补充参数位”，不得补造数值。
4. 检查图片格式、大小和可能的竞品混入风险。

### 6.2 阶段二：底图净化

该阶段可跳过，但必须记录跳过原因。

- 展示原图、处理中、净化结果。
- 支持接受结果、重新生成、跳过。
- 模型必须具备图片输入、图片编辑或图生图、参考图能力。
- 净化结果必须保持产品品类、轮廓、比例、结构、颜色、材质、Logo、包装和可见细节。
- 原图和净化图建立派生关系，不覆盖原图。

### 6.3 阶段三：视觉策划与提示词

拆分为两个可观察步骤：

1. **产品视觉识别**：外观锁定描述、可见文字、材质、结构、风险、待确认事实。
2. **策划与提示词生成**：主图规划、详情页规划、逐张提示词、文字模块和平台限制。

用户可编辑并保存版本：

- 外观锁定描述。
- 主图/详情页数量和顺序。
- 页面职责、卖点和占位参数。
- 单张提示词和禁止内容。

编辑结果提交时，服务端只接受通过对应 Schema 的字段，不允许用任意 JSON 覆盖任务结果。

### 6.4 阶段四：分批生图

- 默认按提示词顺序逐张生成。
- 提供批量提交开关，但服务端仍按并发上限拆分执行。
- 主图默认 `1:1`，详情页默认 `3:4`。
- 每个生图 Item 显示 `pending/running/completed/failed/skipped`。
- 支持单张重试、批次重试和暂停后继续。
- 每次执行使用幂等键，避免重复点击生成重复图片。

文件名规则：

```text
[产品名]_主图_[序号]_[关键词].png
[产品名]_详情页_[序号]_[关键词].png
```

产品名和关键词必须经过文件名清洗；重名时追加任务短 ID 和版本号。

### 6.5 阶段五：质检与返修

每张图输出结构化质检结果：

```ts
type QualityCheckItem = {
  key: string;
  status: 'passed' | 'warning' | 'failed' | 'manual_override';
  score?: number;
  evidence?: string;
  modelId: string;
  checkedAt: string;
};

type QualityCheckResult = {
  overallStatus: 'passed' | 'needs_repair' | 'needs_review';
  items: QualityCheckItem[];
  blockingIssues: string[];
  reviewedByUser: boolean;
};
```

十项检查：外观一致性、主体辨识度、信息真实性、版式与文字、详情页决策链、视觉统一性、道具从属性、安全边距、点击转化力、拼接适配度。

完成门禁：

- `failed` 项必须返修，或由用户明确执行 `manual_override`。
- `warning` 项允许用户确认后继续。
- 质检结果和人工豁免必须写入事件记录。

固定返修动作：外观变形、文字乱码、虚构参数、设计质感不足。返修创建新资产版本，原图只读保留。

## 7. 模型选择交互

### 7.1 模型唯一来源

设置页是唯一维护入口。工作流只读取模型安全摘要，不接受 API Key、Base URL 或完整配置。

每个步骤可以选择：

- 使用该步骤推荐模型。
- 跟随上一步模型。
- 从满足能力的模型中单独选择。

### 7.2 能力矩阵

| 步骤 | 必需能力 |
|---|---|
| 产品识别 | `vision`、`jsonMode` |
| 可见文字识别 | `vision`、`ocr`、`jsonMode` |
| 提示词策划 | `jsonMode` |
| 底图净化 | `imageEditing`、`referenceImage` |
| 主图/详情页生成 | `imageGeneration`、`referenceImage` |
| 视觉质检 | `vision`、`jsonMode` |
| 图片返修 | `imageEditing`、`referenceImage` |

只展示当前用户、已启用、实测通过且能力匹配的模型。模型停用或实测失效时，草稿保留但执行按钮禁用。

## 8. 任务、恢复和并发

### 8.1 任务状态

```text
draft
  -> running_step
  -> awaiting_review
  -> running_step
  -> completed

running_step -> partial_failed -> retry / continue
running_step -> failed
```

服务端维护唯一状态，前端不能直接推进状态。任务和步骤都携带 `version`，更新时必须提交 `expectedVersion`。

### 8.2 重复请求

- 执行、审批、重试接口必须支持 `Idempotency-Key`。
- 同一个任务同一个步骤同一个版本只能有一个运行实例。
- 并发审批返回冲突错误，前端重新拉取任务详情。
- 已确认的上游结果不因下游失败而清空。

### 8.3 资产版本

每次生成或返修都创建新资产版本，至少记录：任务 ID、来源资产 ID、步骤 ID、版本号、提示词、模型快照和创建时间。

## 9. 空状态、异常和权限

- 没有可用模型：显示具体缺失能力和设置页入口。
- 上传失败：保留成功文件，单独展示失败原因。
- 模型能力不足：执行前拦截，不产生上游请求。
- 上游超时、429、5xx：保留输入并允许重试。
- 越权任务、模型或资产：统一返回资源不存在，不泄露归属信息。
- 用户刷新页面：通过任务详情恢复步骤、输入、模型选择和结果。
- 删除草稿不自动删除原始图片和已生成资产。

## 10. 验收标准

- 进入 `/marketing2` 首先看到五张工作流卡片。
- 每张卡片的输入、输出、依赖和缺失条件可解释。
- 草稿、最近任务、继续任务和历史导入可用。
- 每一步可选择不同的设置模型，并保存模型快照。
- 执行、审批、重试不会因重复请求产生重复 Item 或重复资产。
- 失败项可单独处理，原始结果和资产版本不被覆盖。
- 质检结果结构化，失败项有明确返修或人工豁免路径。
- 1440×900、1024×768、390×844 无横向溢出、遮挡和不可操作控件。
- 键盘可以完成卡片选择、步骤切换、模型选择和主要操作。
